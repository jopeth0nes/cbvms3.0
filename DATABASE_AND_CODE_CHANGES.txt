- Guardian fields are not included in the current forms or database setup.

NEW DATABASE CRUD CALLS
File: database/student_management.py
These methods are available through the CBVMSDatabase object (db).

1. UPDATE: db.update_student_details(...)
   Saves academic status, student email, mobile number, and verification state.
   Also INSERTS a status-history record when status or verification changes.

2. READ: db.get_student_status_history(student_id)
   Retrieves status changes, reasons, administrator names, and timestamps.

3. CREATE: db.impose_suspension(...)
   INSERTS a suspension with its reason, start/end dates, assigning administrator,
   and optional related violation ID.

4. UPDATE: db.lift_suspension(...)
   Records who lifted/cancelled a suspension, when, and why.
   Keeps the original suspension record.

5. READ: db.get_active_suspension(student_id)
   Retrieves the suspension active at the current time.
   Timed suspensions stop being active at their end time without deleting history.

6. READ: db.get_suspension_history(student_id)
   Retrieves active, scheduled, expired, and lifted suspension records.

7. CREATE / UPDATE: db.record_premises_entry(student_id)
   INSERTS a Graduate/Unenrolled premises entry or UPDATES its last-seen time
   when repeated camera sightings belong to the same visit.

8. READ: db.get_premises_entries(search="", status="All")
   Retrieves the latest 1,000 matching premises entries.

9. DELETE: No new delete commands were added.

EDITED DATABASE CALLS
File: database/db_manager.py

1. db.initialize()
   Calls migrate_student_management(conn).
   Adds missing fields/tables using ALTER TABLE and CREATE TABLE IF NOT EXISTS.

2. db.insert_student(...)
   Added optional contacts and registration_pending arguments.
   Validates and saves student contact information and verification state.
   Existing callers remain compatible.

3. db.get_all_students() / db.get_student(...)
   Changed their SELECT queries to return all student fields, including new ones.

4. db.record_attendance(...)
   Checks current academic status and registration verification before saving.
   Graduate, Unenrolled, and unverified registrations do not create attendance.

5. db.log_violation(...)
   Checks current academic status and registration verification before saving.
   Blocks new violations for Graduate, Unenrolled, and unverified registrations.
   Existing unknown-person security logging remains.

DATABASE CRUD CALLS ADDED / COMPLETED

1. CREATE: db.insert_appeal(violation_id, student_id, reason, evidence=picture)
   Alias: db.submit_appeal(...)
   picture is a tuple: (filename, "image", raw_picture_bytes).
   Example: evidence=("proof.jpg", "image", picture_bytes).
   A picture is required. Supported formats: JPG/JPEG, PNG, BMP, up to 10 MB.
   The explanation must contain 20–1000 characters, matching the existing UI.
   INSERT INTO appeals and INSERT INTO evidence_files occur in one transaction.
   Failed evidence storage rolls back the whole submission and creates no alert.
   Ownership, active strike, confirmation, deadline, and duplicate submission
   checks are enforced before saving. The server clock is checked after acquiring
   the database write lock, so waiting for a lock cannot bypass the deadline.
   Existing exact-boundary behavior is retained: accepted at the precise deadline,
   rejected after it. A successful submission returns its appeal ID; failure returns None.

2. READ: db.get_admin_appeal_alerts()
   SELECTs appeals joined to student and violation information.
   Returns submission alerts, appeal status, and persisted read state.

3. READ: db.admin_appeal_unread_count()
   SELECT COUNT(*) FROM appeals WHERE admin_alert_read = 0.

4. UPDATE: db.mark_admin_appeal_alert_read(appeal_id)
   UPDATE appeals SET admin_alert_read = 1 WHERE id = ?.
   Omitting appeal_id explicitly marks all appeal alerts as read.
   Merely opening the Alerts page does not call this command.

5. CREATE: db.insert_evidence_file(appeal_id, student_id, filename, file_type, file_data)
   The existing secondary evidence helper now validates the picture, ownership,
   and pending appeal status before inserting. It cannot accept PDF/TXT files.
   New appeal submissions use insert_appeal(evidence=...) instead, ensuring the
   initial appeal and its required picture are committed together.

6. UPDATE: db.update_appeal_decision(appeal_id, decision, admin_notes, decided_by=...)
   The existing transaction still updates appeal status, strike effects, history,
   and the student's in-app notification together.
   RecordsPanel now passes the actual logged-in admin username as decided_by.

7. READ: db.get_appeal_eligibility(violation_id, student_id)
   Existing backend method reused by the page and open-form buttons every second.
   The submission transaction independently enforces the same eligibility rules.
